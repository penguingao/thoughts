In order to make Envoy, a L7 network proxy that operates mainly on byte streams,
an AI native proxy, we need it to parse and transform the HTTP payload in
addition to the HTTP header and tarilers.

A network proxy's main job is to provide routing (discovery, and LB) and auth.
The proxy makes these decisions based on policy and real time telemetry (network
path health, system load, and application end point load). This way the
application endpoints can focus on application logic.

While LLM and AI agents are a form of more specialized application endpoints,
they also require routing and auth ("AI application governance"). However, to
make effective routing and auth decisions, the HTTP playload needs to be parsed
and manipulated. This is mainly due to the fact that LLM and MCP requests are
heavily contextualized. e.g. An LLM inference request caries the full
conversation history or an id for each interaction; MCP requests fall into a
session which contains auth, tool discovery results, pending tool calls,
resource update, and other statefull interactions between the client and server.
The context can only be learned by looking into the historically opaque HTTP
payload.

# Envoy's extensibility

Envoy's HTTP extensions struggle to meet the AI workload's requirement mainly
due to:
- HTTP payload is exposed to the HTTP filters as stream of unstructured bytes,
  one chunk at a time
- Once the byte stream is processed and forwarded, it's forgotten
This maintains reasonable memory footprint.

This limits what can be easily achieved by the Envoy proxy:
- Effective routing needs to be done after the prompt in the payload being
  processed and validated. Before routing, the Envoy has to hold onto the
  payload
- The JSON message needs to be fully processed before the Envoy can know its
  validity (duplicated fields get around auth), and make sure the data needed
  for routing is valid 
- Once a request is sent to a backend, it cannot be retried

This calls for a different programming model. This is a the motivation behind
https://github.com/envoyproxy/envoy/issues/44681.

The filter has been a successful way to introduce extensions into the Envoy - it
balances complexity and flexibility well by linearizing the logically steps of a
request handling, so that the extensions can be composable while being largely
independent in their implementations.

To better support LLM and AI agent traffic, we would like to design AI filter
semantics for it to process the structured JSON message, while maintaining the
composibility and flexibility.

# Premise: Buffer offload to storage

It is necessary for the proxy to hold the entire HTTP payload before it can
validate the data and make the routing decision. This calls for a buffer
implementation that is detached from the HTTP stream buffer management. To be
cost effective, this buffer should have the option of being offloaded to
storage / SSD.

The storage offload also enables request retry.

In the environments where memory is not constrained, the buffer implementation
can simply be a different pool of memory than the Envoy's streaming buffer.

# AI filter semantic

We want to provide convenience to process most requests, while being
flexibile to deal with potentially large payloads seen in multi-modal models.

The first thing a filter can do is to `co_await getRequest()`, which returns an
`InferenceRequest` that is a `nlohmann::json` object, with some special
modification. This is a class that has convenient methods to access common
fields like `model`, `messages`, `tools`, `metadata`,
`reasoning`, `service_tier`, `stream`. To start, we aim to be compatible to both
OpenAI's [Chat Completions API](https://developers.openai.com/api/reference/resources/chat)
and later the newer [Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create).
The Completions API serves as the de facto standard for LLM inference, and most
of the LLM inference providers either directly mirror its structure (OpenRouter,
DeepSeek, Mistral, Kimi, Qwen, GLM, etc) or offer a compatible layer on top of
their native API (Gemini API on server, Anthropic in client SDK).

OpenAI is also pushing for the migration to the more stateful Response API,
which can be translated into from the Completetion API. Envoy should be able to
provide Response API to Completeion API by storing the server state, and
offloading the server side tool calls. This can be a competitive edge to help
developers use the newer API with legacy APIs, while avoiding the provider
storing their data.

`nlohmann::json` supports a binary type, which can be tagged with a `subtype`.
For fields that can be potentially large - larger than the Envoy's per stream /
request memory footprint, we can store the to the external buffer in the binary
field with a `subtype` tagged.

The filters will be able to take this as a handle to stream process the bytes if
it needs, which is described in the later sections.

## StreamableBuffer

The pointer in the `nlohmann::json` binary subtype can be used to consturct a
`StreamableBuffer`.

The filter can express whether it wants to stream process any of them. The
`StreamableBuffer` will be streamed to the filter in a predefined order for
example: `prompts` -> `tools` -> `other_unknown_fields`.

The filter is informed of the ordering with the associated json path of these
fields.

At the streaming time, the filter is given a pair of `receiver` and `forwarder`
methods for each streamable slice.

## Filter's overall control flow

In the most basic case, all fields including the prompts are inline of the
request. The filter can directly forward the request for the next filter to
perform its work.

This doesn't always work in the following example cases:
- the filter wants to process some prompts before deciding if it wants to insert
  tools
- the filter wants to stream process the full prompt before forwarding to
  perform guardrail, semantic routing, etc
- the filter wants to look at `tools` first before `prompts`

In all of these cases, we can hold the `AiRequest` in the current filter,
and start stream the streamable buffers. However, the `forwarder` would
actually detect if a buffer is modified, and decide to write it back to external
buffer, or simply drop it because the original copy is sitll in the external
buffer.

In the case a filter wants insert a field, it will receive a `receiver` that
returns nothing and a `forwarder` at the appropriate time.

Once the filter has done this pass of fields, it can then forward the request,
and optentially stream process another not-necessarily-overlapping set of
fields.

```
          |
     get_request
          |
  regiester_interest
        /   \
       /     \
      /       \
stream_slices  |
     |         |
     \         /
      \       /
       \     /
        \   /
   forward_request
          |
     stream_slices
          |
```

This is the scheme that trades the memory footprint with some level of
inconvenience for more advanced / special use cases. It relies on the fact that
the external buffer can be stream processed multiple times more or less
efficiently.

We believe that vast majority of networking proxy related features / logics can
be expressed in this two-pass streaming scheme.

The two streaming passes don't have to have the same set of interests.

## Managing the complexity of the filter manager

With the help of C++ coroutine, we can express the filter as a few sequential
processing units.

At a given time, each streaming buffer has a source, a sink, and a number of
forwarder.

The source and sink are managed by the filter manager that keeps track of how
many bytes have been read out of and wirtten back to the external buffer. Each
slice of the data is sent through the filters by the filter's `receiver` and
`forwarder` forming a logical linked list. Once the slice reaches the end of the
chain, it is sent to the sink to write back or drop.

When a filter starts streaming slices before `forward_request`, it is the end of
the chain by definition, so the filter manager sinks the bytse.

When a filter starts streaming slices after `forward_request`, it is a
forwarder, so it's `forwarer` simply passes the data to the next filter after
its processing.

Once the `AiRequest` eaches the end of the filter chain, the filter
manager assumes that the filter chain is ready to stream out the data as json
payload back to HTTP payload.

# Sample Filter

```c++

// Describes what happens to the request after `decode()` `co_return`s.
enum class PostDecodeAction {
 // Skip means the filter is no longer interested in any `StreamableBuffer`s,
 // even if it has register interest to stream.
 Skip;
 // Reset means the filter would like to reset the request.
 Reset;
};

class AiRequest : nlohmann::json {
 public:
  // registers the json path to be streamed.
  void registerForStream(absl::AnySpan<absl::string_view> path);

  Stream();
};

class AiRequestGetter {
 public:
  Coroutine::Task<absl::StatusOr<std::unique_ptr<AiRequest>>> operator() () && = 0;
};

class AiRequestForwarder {
 public:
  // json path of the fields that will be streamed.
  Coroutine::Task<absl::StatusOr<> operator() () && = 0;
};

class FieldStreamer {
 public:
  Coroutine::Task<absl::StatusOr<StreamableBuffer>> next();
};

class StreamableBuffer {
 public:
  absl::string_view json_path();
  Coroutine::Task<absl::StatusOr<std::optional<Chunk>>> recv();
  Coroutine::Task<absl::Status> forward(Chunk chunk);
};

Coroutine::Task<absl::StatusOr<PostDecodeAction>> decode(
  AiRequestGetter req_getter, AiRequestForwarder req_forwarder) {
  ASSIGN_OR_CO_RETURN(std::unique_ptr<AiRequest> req, co_await std::move(req_getter)());

  // process model name, etc
  for (const Message& message : req.messages()) {
    // message.role is a string
    // message.type is a string
    // message.name is a string
    // message.content_type is a string
    // message.content is either a string or a `StreamableBufferIdx`
    req.registerForStream(message.content);
  }
  for (const Tool& tool : req.tools()) {
    // tools are typically all inlined, but can contain `StreamableBufferIdx` in
    // description
  }

  auto helper = [&](StreamableBuffer&& buf) {
    // buf might be empty - this is when a filter can inject streamable data.
    ASSIGN_OR_CO_RETURN (const std::optional<Chunk> c, co_await buf.recv());
    while (c.has_value()) {
      // read c.data() as const std::string
      CO_RETURN_IF_ERROR(co_await buf.forward(c));
    }
    co_return absl::OkStatus();
  };
  FieldStreamer streamer = req.Stream();
  ASSIGN_OR_CO_RETURN(std::optional<StreamableBuffer> s, co_await
    streamer.next());
  while (s.has_value()) {
    CO_RETURN_IF_ERROR(helper(s));
    ASSIGN_OR_CO_RETURN(s, co_await streamer.next());
  }

  // optionally resetStreamInterest and registerForStream again.
  FieldStreamer streamer = req_forwarder(std::move(req));

  // optionally stream again
  // ...

  co_return PostDecodeAction::Skip;
}

```

# Request Schema and Ai filters
Each request can be parsed according to a given schema, e.g.
`OPENAI_CHAT_COMPLETION`, `VETEXT_GENERATE_CONTENTS`, etc.

We make each filter configure what type of
request it can process - this way, we can share some generic filters across
different end points - llm vs audio vs embedding vs MCP, etc.

We should provide accessor classes that knows how to access all major LLM
inference schema in a generic way for commonly used functionalities. So that
filters using them can easily support a family of schemas easily.

These classes require a field map that can be used to perform provider /
endpoint transcoding.

Some implementation notes:

DFS traversal of JSON. Use the schema to arbitrate same level ordering.

Early return handling: any data that's read, but not forwarded is lost. any data
that's not read, will be automatically rolled to the next filter.

only start streaming if we reach end of request forwarder or a filter starts
streaming. (can optimize to start early if the first buffer in queue is
interested, and a filter has forwarded the request. we can optimize to overlap
stages - a field will be processed by source() if the previous stage has
finalized the given field)

Each stage's sink should open a new external buffer, and write modified buffers
to it. This means JsonWithExternalBuffer should handle multiple external buffer
references. The sink should be interested the union of all the previous filter's
interests. If it's the sink at the end of the filter chain, it is interested in
all fields so that it could re-serialize the full json payload.

The last sink should reserialize the json dom back to HTTP filter chain, while
building a new JsonWithExternalBuffer object with offloaded fields pointing to
the new offsets of the resrialization. This is useful for later filters who
might want to access the JSON payload without parsing the dom themselves. It
could be a later of instance of APM itself. This makes it possible to split the
APM into multiple places of the HTTP filter chain and make the last one do the
transcoding.

The later APM will have the guarantee that fields come in the correct order. If
its filter chain is single pass, no further external buffer is involved.

If it's multi-pass, its sink should try to stream all offloaded fields and store
them to a new external buffer.
