Envoy has traditionally been an L7 network proxy that performs its L7
functionalities mainly based on HTTP headers, mostly treating the HTTP payload
as opaque data.

A network proxy's main job is to provide routing (service discovery and load
balancing) and auth. The proxy makes these decisions based on policy and
real-time telemetry (network path health, system load, and application endpoint
load). This way, application endpoints can focus purely on application logic.

As more specialized application endpoints, LLMs and AI agents also require
routing and auth ("AI application governance"). However, to make effective
routing and auth decisions, the HTTP payload needs to be parsed and manipulated.
This is mainly due to the fact that LLM and MCP requests are heavily
contextualized. For example, an LLM inference request carries the full
conversation history or a session ID for each interaction; MCP requests belong
to a session containing auth tokens, tool discovery results, pending tool calls,
resource updates, and other stateful interactions between the client and server.
This context can only be learned by inspecting the historically opaque HTTP
payload.

To transform Envoy into an AI-native proxy, we need it to effectively parse and
transform the HTTP payload while maintaining strict per-stream and
per-connection memory bounds to protect against denial-of-service attacks.

# Envoy's extensibility

Envoy's extensibility is one of the main reasons for its popularity. However, AI
workloads introduce significant challenges. Envoy's existing HTTP extension
model struggles to quickly and easily support features for AI workloads, mainly
because:

-   The HTTP payload is exposed to HTTP filters as a stream of unstructured
    bytes, one chunk at a time.
-   Once the byte stream is processed and forwarded, it is discarded.

This limits what can be easily achieved by Envoy:

-   Effective routing can only happen after the prompt in the payload is
    processed and validated. Prior to routing, Envoy must hold onto the payload.
-   The JSON message needs to be fully processed before Envoy can verify its
    validity (e.g., detecting duplicate fields used to bypass auth) and ensure
    the data needed for routing is valid.
-   Once a streaming request is sent to a backend, it cannot be retried.
-   If multiple filters are needed, repeated parsing and reserialization are
    necessary.

This calls for a different way of extending Envoy, which is the motivation
behind https://github.com/envoyproxy/envoy/issues/44681.

The concept of a "filter" has been a successful way to introduce extensions into
Envoy—it balances complexity and flexibility well by linearizing the logical
steps of request handling, allowing extensions to remain composable while being
largely independent in their implementations.

To better support LLM and AI agent traffic, we want to design AI filter
semantics to process structured JSON messages while maintaining composability
and flexibility.

# Premise: request buffer offload to storage

It is necessary for the proxy to hold the entire HTTP request payload before it
can validate the data and make routing decisions. This calls for a buffer
implementation detached from HTTP stream buffer management. To be
cost-effective, this buffer should support offloading to storage / SSDs.

Storage offloading also enables request retries.

In environments where memory is not constrained, the buffer implementation can
simply be a separate memory pool rather than Envoy's streaming buffer.

# Structural control data and payload

In standard HTTP, control data resides in headers, while the payload resides in
the body. This separation enabled effective HTTP filter chains in Envoy.

Unlike HTTP headers, which are small enough to fit in memory at scale, JSON has
a tree-like structure. There is no native boundary separating control data
(model ID, service tier, load balancing parameters, cache control) from the
payload (tool definitions, tool calls, images, prompts).

To effectively extract structural control data, we can parse the JSON document's
tree structure, keeping control data in the tree and representing potentially
large payload fields as pointers into the buffered HTTP payload. This tree
mirrors the real JSON payload and serves as an index over the HTTP payload. For
the convenience of this document, we call this tree the **AI request index**.

For the vast majority of proxy features, filters only need to read and modify
the AI request index. Once these operations are done, Envoy reserializes the
HTTP payload based on the index and the pointers into the buffered original
payload.

These operations can be modeled as a filter chain. The end of the filter chain
is responsible for reserialization, analogous to an HTTP codec.

# AI filter

## Semantic requirements

The semantics of an AI filter should feel familiar. Like HTTP filters, it
defines two independent logical flows: decode (request path) and encode
(response path).

### Request
Taking the decode path as an example, the logical flow is:

-   Receiving and optionally manipulating the request index - analogous to HTTP
    headers
-   Propagate the index to later filters - analogous to stop iteration and
    continue
-   If desired, receiving, buffering, optionally modifying the request payload -
    analogous to decode / encode data
-   Propagate the payload to later filters

In some cases, a filter might not be able to finalize its operations on the
request index before inspecting some of the payload. We can benefit from the
fact that the payload is already fully buffered: namely, the filter can stream
the payload before it forwards the index to the next filter.

However, if every filter independently streams the payload from disk, it
generates excessive I/O overhead. To mitigate this, we want to share and
coalesce I/O as much as possible across the chain of filters.

### Response
Response processing is different from request processing in that we don't want to buffer
the full response stream before sending the first byte to the end user:

-   Time to first token is important to user experience, which is why a lot of
    LLM endpoints utilize Server-Sent Events (SSE) to stream the response.
-   There is not a lot of value in buffering the full response stream: the server responses
    are generally well structured and valid, and there is no need to perform request-level
    retries with the response body.

This calls for distinct handling between unary JSON responses and streaming SSE responses:

-   **Unary JSON responses:** Unary responses can be large (10MB–50MB+ for large tool outputs,
    code generation, or embeddings). To strictly bound memory without buffering the entire
    body, unary responses stream leaf fields incrementally (`AiResponseField`).
-   **SSE streaming responses:** Individual SSE frames (demarcated by `\n\n`) are typically
    tiny (50B–2KB token deltas). Buffering individual SSE frames is completely practical and
    allows the decoder to resolve SSE metadata (`event:`, `id:`, etc.) and parse the complete
    JSON DOM before handing it to filters.

    However, SSE events can also carry raw non-JSON bytes (such as multimodal real-time audio
    chunks, binary data, or large server-side error dumps) that may be large (megabytes). To
    prevent allocating large contiguous heap memory, Envoy supports streaming raw bytes in bounded
    chunks (`Buffer::Instance`) with watermark backpressure. In atypical cases where an oversized
    frame must be buffered or held, the payload can be offloaded to an external buffer
    (`JsonWithExtBuf` / storage) to strictly preserve memory bounds.

We also want to be able to perform transcoding in a streaming fashion.

## Overall control flow of an AI filter

On the request path, a filter is given access to the AI request index first. In
the simplest case, it reads and optionally modifies the index, then forwards the
index to the next filter. This satisfies most basic auth, routing, and
transcoding use cases.

If deep inspection of the large payload is required, a filter may register with
the filter manager the JSON fields that it wants to stream-process. After
registration and forwarding the index, the filter starts stream-processing the
fields. The fields are streamed to it in an order dictated by the filter manager
based on the request's JSON schema. This is the second common case, enabling
payload-based auth and tool modifications.

If a filter needs to perform model routing based on the payload, it can start
streaming the payload before forwarding the index. In this case, downstream
filters cannot see the index or payload until this completes. After this, it may
optionally register a separate (or not-necessarily-overlapping) set of fields to
stream-process again after forwarding the index. This second pass is useful in
rare cases where a filter cannot make its decisions based strictly on the filter
manager's dictated schema order.

On the response path, filter handling is separated based on the response mode:

-   **SSE streams (`encodeSSE`):** The filter coroutine runs for the entire lifetime of the
    response stream. It receives discrete `SseEvent` frames that contain the resolved event
    metadata (e.g., `event: content_block_delta`), comments, and the parsed JSON DOM (or raw text
    for events like `data: [DONE]`). Filters can easily read and mutate the JSON DOM without
    writing complex streaming state machines across leaf chunks, while coroutine-local variables
    naturally maintain cross-frame state (e.g., token usage accounting, multi-delta PII / guardrail
    scanning, or frame-level buffering / batching).

    If an event carries large raw non-JSON data (such as real-time audio streams), `SseEvent`
    exposes the data via `Buffer::Instance` and supports multi-chunk streaming with an `end_of_event`
    indicator, allowing filters to stream or forward raw bytes with watermark flow control.
-   **Unary responses (`encodeUnary`):** A filter receives a stream of JSON fields as they are
    parsed, performing information extraction and/or transcoding with strictly bounded memory.
    It can choose to buffer as many JSON fields as needed before forwarding them in rare cases.

## API design

In addition to the semantic requirements, it is desirable to provide intuitive
API to allow developers to focus on core logic instead of dealing with framework
complexity.

We choose to make use of C++20 coroutine, because it naturally models the
sequential nature of a filter.

```cpp
class AiRequest;
class FieldStreamingSession;
class FieldStreamReceiver;

// Receiver for a field stream. It contains the metadata of the field being streamed
// (e.g., json_path / field schema identifier) and provides a callable awaitable to
// read incoming buffer chunks.
class FieldStreamReceiver {
public:
  absl::string_view field_path() const;

  // Callable awaitable to receive the next buffer chunk of the field.
  // Returns Buffer::InstancePtr or std::nullopt at the end of the field stream.
  Coroutine::Task<absl::StatusOr<std::optional<Buffer::InstancePtr>>> operator()();
};

// Callable awaitable to propagate buffer chunks to the outgoing stream.
using FieldStreamPropagater =
    absl::AnyInvocable<Coroutine::Task<absl::Status>(Buffer::InstancePtr)>;

// Callable awaitable that a filter uses to receive `AiRequest`. Callable on rvalue only,
// documenting that it should only be used once.
using AiRequestReceiver =
    absl::AnyInvocable<Coroutine::Task<absl::StatusOr<AiRequest>>() &&>;

// Callable awaitable that propagates the `AiRequest` to the next filter in the chain. Callable
// on rvalue only, documenting that it should only be used once.
using AiRequestPropagater =
    absl::AnyInvocable<Coroutine::Task<absl::StatusOr<FieldStreamingSession>>(
        AiRequest, std::optional<FieldStreamingSpec>) &&>;

using LocalReplier =
    absl::AnyInvocable<void(Http::Code code, std::string details) &&>;

// Discrete Server-Sent Event (SSE) frame.
class SseEvent {
public:
  // SSE event name (e.g., "message", "content_block_delta", "error").
  absl::string_view event() const;
  void set_event(absl::string_view event);

  // SSE event ID for reconnection.
  absl::string_view id() const;
  void set_id(absl::string_view id);

  // SSE retry interval in milliseconds.
  std::optional<uint32_t> retry() const;
  void set_retry(std::optional<uint32_t> retry);

  // SSE comment line (e.g., ": ping\n\n").
  absl::string_view comment() const;
  void set_comment(absl::string_view comment);

  // True if the event data is valid JSON.
  bool is_json() const;

  // Parsed JSON DOM of the frame. In atypical cases where the frame was offloaded,
  // this is backed by JsonWithExtBuf.
  const nlohmann::json& json() const;
  nlohmann::json& json();

  // Raw non-JSON payload:
  // Convenience accessor for small text strings (e.g. "[DONE]" terminal event or errors).
  absl::string_view raw_data_as_string() const;

  // Chunked buffer accessor for arbitrary or large raw non-JSON bytes (audio deltas,
  // binary blobs, large text dumps). Supports zero-copy moves and external buffer slices.
  const Buffer::Instance& raw_data() const;
  Buffer::Instance& raw_data();
  void set_raw_data(Buffer::InstancePtr raw_data);

  // Chunking indicator for oversized raw events:
  // Returns true for standard frames, or for the terminal chunk of a multi-chunk raw event.
  bool end_of_event() const;
};

// Returns std::nullopt at the end of the SSE response stream.
using SseStreamReceiver =
    absl::AnyInvocable<Coroutine::Task<absl::StatusOr<std::optional<SseEvent>>>()>;

using SseStreamPropagater =
    absl::AnyInvocable<Coroutine::Task<absl::Status>(SseEvent)>;

using FieldPath = absl::Span<const std::variant<absl::string_view, size_t>>;
class AiResponseField {
public:
  FieldPath field_path() const;
  // The node is guaranteed to be a leaf type in nlohmann::json::value_t:
  // null, boolean, number_*, string, binary. For string and binary, this might be
  // a partial chunk of the field, in the case that the value is too big to
  // fit in the streaming buffer.
  const nlohmann::json& node() const;
  nlohmann::json& node();
};

// Empty vector is end of current message.
using AiResponseStreamReceiver =
    absl::AnyInvocable<Coroutine::Task<absl::StatusOr<std::vector<AiResponseField>>>()>;

using AiResponseStreamPropagater =
    absl::AnyInvocable<Coroutine::Task<absl::Status>(std::vector<AiResponseField>)>;

// Abstract interface implemented by `AiFilter` instances.
// The filter's factory should allow it to declare what AI protocol / schema it
// supports.
class AiFilter {
public:
  virtual ~AiFilter() = default;

  // Invoked when an AI request arrives.
  // Returns absl::OkStatus() on normal completion, or an error status on failure.
  virtual Coroutine::Task<absl::Status> decode(AiRequestReceiver receive_request,
                                               AiRequestPropagater propagate_request,
                                               LocalReplier reply_locally) = 0;

  // Invoked for Server-Sent Events (SSE) streaming responses. The coroutine runs
  // for the entire lifetime of the response stream, receiving and propagating
  // discrete SseEvents.
  virtual Coroutine::Task<absl::Status> encodeSSE(
      SseStreamReceiver receive_sse,
      SseStreamPropagater propagate_sse) {
    ASSIGN_OR_CO_RETURN(auto event, co_await receive_sse());
    while (event.has_value()) {
      CO_RETURN_IF_ERROR(co_await propagate_sse(std::move(*event)));
      ASSIGN_OR_CO_RETURN(event, co_await receive_sse());
    }
    co_return absl::OkStatus();
  }

  // Invoked for unary JSON HTTP responses. Receives and propagates leaf fields
  // in a streaming fashion.
  virtual Coroutine::Task<absl::Status> encodeUnary(
      AiResponseStreamReceiver receive_response_stream,
      AiResponseStreamPropagater propagate_response_stream) {
    ASSIGN_OR_CO_RETURN(auto fields, co_await receive_response_stream());
    while (!fields.empty()) {
      CO_RETURN_IF_ERROR(co_await propagate_response_stream(std::move(fields)));
      ASSIGN_OR_CO_RETURN(fields, co_await receive_response_stream());
    }
    co_return absl::OkStatus();
  }

  // Synchronous request context accessors can be provided: `StreamInfo`, HTTP
  // headers, etc.
};

class FieldStreamingSpec {
public:
  void addFieldForStreaming(absl::string_view json_path);
};

// `AiRequest` represents the structured request payload presented to an `AiFilter`.
// It wraps a JsonWithExtBuf document and manages registration of field paths
// that the filter wants to stream.
class AiRequest {
public:
  // Index access
  const JsonWithExtBuf& request_index() const { return index_; }
  JsonWithExtBuf& request_index() { return index_; }

  // Starts a filter streaming stage ending at this filter.
  // Captures current registered paths and clears registered_paths_ for subsequent stages.
  FieldStreamingSession stream(FieldStreamingSpec);
};

```

## Developer ergonomics considerations

### Early return

We allow a filter to early return `absl::OkStatus()` once it's done processing
the request. A filter is responsible for propagating anything it has received.
Anything it hasn't received, even if it has registered interest, safely bypasses
an early-returned filter.

This allows an AI filter to stay small if it only wants to see part of the
request.

### Canonical Intermediate Representation (IR) and Transcoding Architecture

For MCP and A2A, we should provide helper utility classes that simplify
accessing and manipulating `request_index()`.

For LLM inference requests and responses—which face a fragmented landscape of provider schemas (OpenAI, Anthropic, Gemini, Mistral, Bedrock, etc.)—we adopt a **Canonical Intermediate Representation (IR)** architecture, borrowing the core design principle from modern optimizing compilers:

```
[Downstream Client]
        │
        ▼  (Client Format, e.g. Anthropic Messages API)
┌────────────────────────────────────────────────────────────────────────┐
│  Client Adapter Filter                                                 │
│  - decode: Client Format ──► Canonical IR (OpenAI Chat Completions)    │
│  - encode: Canonical IR  ──► Client Format                             │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │  Canonical IR
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│  Intermediate AI Filters (Completely Schema-Agnostic!)                 │
│  - Auth & Model Routing                                                │
│  - Token Counting & Rate Limiting                                      │
│  - Guardrails, Prompt Injection & PII Masking                          │
│  - Observability & Semantic Caching                                    │
│  (All operate strictly on Canonical OpenAI format!)                    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │  Canonical IR
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│  Upstream Provider Adapter Filter                                      │
│  - decode: Canonical IR          ──► Upstream Format (e.g. Gemini/Bedrock)│
│  - encode: Upstream Response SSE ──► Canonical Response IR (OpenAI)    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼  (Upstream Provider Wire Format)
                             [Upstream LLM]
```

#### Canonical IR Definition
We select OpenAI's [Chat Completions API](https://developers.openai.com/api/reference/resources/chat) as the canonical IR because it serves as the de facto industry standard: most LLM inference providers either directly mirror its structure (OpenRouter, DeepSeek, Mistral, Kimi, Qwen, GLM, etc.) or offer compatibility layers on top of their native APIs.
- **Request IR:** Normalized `request_index()` tree based on Chat Completions (`messages`, `tools`, `model`, etc.), preserving provider-specific extension attributes in extra metadata fields.
- **Response IR:** Normalized `chat.completion.chunk` delta structure in `SseEvent` (for streaming) or standard Chat Completion JSON (for unary).

#### Canonical Filter Chain Composition
Envoy's filter chain executes response (`encode`) filters in the **exact reverse order** of request (`decode`) filters. This symmetric pipeline creates an elegant composition:

1. **Request Decode Path:**
   - **Client Adapter Filter (Ingress Transcoder):** Runs first. Decodes incoming client requests (e.g., Anthropic, Gemini, or raw OpenAI SDK) and normalizes the request index into the Canonical Request IR.
   - **Intermediate Filters (Middle Chain):** Auth, rate limiting, PII masking, Model Armor guardrails, and model-aware routing execute purely on the Canonical Request IR. They are 100% decoupled from third-party vendor schemas.
   - **Upstream Provider Adapter Filter (Egress Transcoder):** Runs last on the request path. Translates the Canonical Request IR into the selected upstream provider's wire format (e.g., Anthropic Messages JSON or Vertex Gemini REST/gRPC).

2. **Response Encode Path (Natural Reverse Execution):**
   - **Upstream Provider Adapter Filter:** Runs **first** on the response path! In `encodeSSE` (or `encodeUnary`), it receives the upstream provider's native response events (e.g., Anthropic `content_block_delta` or Gemini candidate parts) and translates them into the **Canonical Response IR** (OpenAI `chat.completion.chunk` delta events).
   - **Intermediate Filters:** Run in the middle on the response path. Token consumption meters inspect `event.json()["usage"]`, content guardrails inspect `event.json()["choices"][0]["delta"]["content"]`, and audit loggers record canonical output deltas. None of these filters need custom adapters for individual LLM vendors.
   - **Client Adapter Filter:** Runs **last** on the response path (closest to the client). It translates the Canonical Response IR back into the format expected by the client's SDK (or acts as an identity passthrough if the client speaks native OpenAI).

#### Architectural Advantages
- **$O(N)$ vs $O(N \times M)$ Complexity:** Supporting $N$ client SDKs and $M$ upstream backends requires only $N$ client adapters and $M$ upstream adapters ($N + M$) rather than $N \times M$ full cross-transcoders.
- **Ecosystem Extensibility:** Intermediate filters (guardrails, quotas, logging) are written once against the Canonical IR and instantly work with all past, present, and future model providers.
- **Cross-Mode Transcoding via Reusable Middle Filters:** Converting between Unary and SSE is decoupled from vendor formats:
  - *Stream Aggregator Filter:* An intermediate filter that consumes Canonical SSE events in `encodeSSE` and emits a Canonical Unary response to `encodeUnary`.
  - *Synthetic Streaming Filter:* An intermediate filter that consumes Canonical Unary responses in `encodeUnary` and emits Canonical SSE chunks to `encodeSSE`.

OpenAI is also pushing for the migration to the more stateful
[Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create),
which can be translated from Chat Completion API. To support server-side
context / chat history supported by Response API, while being able to use a LLM
provider that only speaks Chat Completion API, Envoy can store the context
/ chat history, perform server-side tool calls during request and response
handling, and translate the result back to the client. This can be a competitive
edge to help developers use the newer API with legacy APIs, while avoiding the
provider storing their data.

## Sample filter

```cpp
Coroutine::Task<absl::Status> Sample::decode(AiRequestReceiver receive_request,
                                             AiRequestPropagater propagate_request,
                                             LocalReplier reply_locally) {
  ASSIGN_OR_CO_RETURN(AiRequest req, co_await std::move(receive_request)());

  // process req.request_index() - extracting information to filter state or
  // dynamic metadata; modifying temperature, service tier; etc

  FieldStreamingSpec streaming_spec;
  streaming_spec.addFieldForStreaming("messages[].content");

  auto helper = [&](FieldStreamReceiver&& receiver,
                    FieldStreamPropagater&& propagater) -> Coroutine::Task<absl::Status> {
    ASSIGN_OR_CO_RETURN(std::optional<Buffer::InstancePtr> c, co_await receiver());
    while (c.has_value()) {
      // read c.data() as const std::string
      CO_RETURN_IF_ERROR(co_await propagater(std::move(*c)));
      ASSIGN_OR_CO_RETURN(c, co_await receiver());
    }
    co_return absl::OkStatus();
  };

  FieldStreamingSession streamer = req.stream(streaming_spec);
  ASSIGN_OR_CO_RETURN(std::optional<FieldStreamReceiver> r, co_await streamer.next());
  while (r.has_value()) {
    // r->field_path() contains the metadata of the field being streamed.
    // make field visible to next filter.
    FieldStreamPropagater p = streamer.propagate(*r);

    // stream process field
    CO_RETURN_IF_ERROR(co_await helper(std::move(*r), std::move(p)));

    ASSIGN_OR_CO_RETURN(r, co_await streamer.next());
  }

  // can optionally stream more fields by passing FieldStreamingSpec to
  // propagate_request.
  ASSIGN_OR_CO_RETURN(FieldStreamingSession session,
                      co_await std::move(propagate_request)(std::move(req), std::nullopt));

  co_return absl::OkStatus();
}
```

## Implementation notes

### Request / Response payload Index

JsonWithExtBuf serves as the index. It is based on `nlohmann::json`, which
supports a binary type, which can be tagged with a `subtype`. For fields that
can be potentially large - larger than Envoy's per stream / request memory
footprint, we can store a reference to the external buffer in the binary field
tagged with a `subtype`.

We probably need a way to easily build a JSON path for any such field to help
filters register streaming interest.

### `FieldStream`

`FieldStreamReceiver` contains the metadata of the field being streamed (such as
its JSON path or field schema identifier), allowing filters to identify the field
and inspect its stream. It also exposes an invocable method to await incoming
buffer chunks for that field. `FieldStreamPropagater` is an invocable method to
propagate chunks to the outgoing stream. Both are managed by the filter manager.

`FieldStream` receives bytes from an incoming `Coroutine::AsyncQueue` and
propagates bytes to an outgoing `Coroutine::AsyncQueue`. During
`FieldStreamingSession::propagate`, the queue is handed to the next filter based
on the interest registration, which causes the `FieldStreamingSession::next` to
resume on the next filter if it's already pending.

### Filter manager

The filter manager's job is to launch all the coroutines of AI filters if they
support the incoming request's schema. It manages the early return of the
coroutines.

Each filter is launched as an independent coroutine. `AiRequestReceiver` and
`AiRequestPropagater` are connected by `Coroutine::AsyncQueue` between
coroutines. If a filter early returns before it receives the request, it is
skipped. If a filter early returns after receiving the request, but before
propagating the request, it is an internal error that causes the request to
fail.

When `AiRequest::stream` is called, or the last filter propagates the request,
the filter manager starts a stage of field streaming. The stage starts at the
first filter that has registered interest via `AiRequestPropagater` but hasn't
seen the fields due to an earlier stage. This, by definition, makes each stage
consist of zero or more filters that have called `AiRequestPropagater`. Only the
last filter in the stage might have called `AiRequest::stream`, in which case,
the fields streamed are the union of all the filters in the stage. If the last
filter in the filter chain calls `AiRequestPropagater`, all fields are streamed,
so that the index is serialized back to the HTTP stream.

Each `FieldStream`'s output queue is handed to the next filter that's interested
in the field. If it hits the end, the filter manager receives it.

If a filter early returns, fields are streamed directly to the next filter,
including the ongoing `FieldStream`. However, any bytes that are not yet
propagated will be dropped. The filter manager essentially connects the
`AsyncQueue` to the next filter when this happens, which means each
`FieldStream` might have multiple input queues.

The `FieldStreamingSession` works with the filter manager to pass queues around,
and understands the "next interested filter" for each field.

```cpp
class FieldStreamingSession {
public:
  // Takes the next field off the queue that is ready for streaming.
  // Returns a FieldStreamReceiver for the field, or std::nullopt if all registered
  // fields in the current stage have completed.
  Coroutine::Task<absl::StatusOr<std::optional<FieldStreamReceiver>>> next();

  // Hands the field stream to the next interested filter in the chain and returns
  // a propagater to write outgoing chunks.
  FieldStreamPropagater propagate(const FieldStreamReceiver& receiver);
};
```

Filter Manager and the APM integrate with upstream and downstream watermark
buffers so that they can receive and apply backpressure callbacks. This is already
in `BufferManager`.

Filter Manager also receives HTTP stream reset callbacks, so that it cancels the
coroutines. Coroutines might asynchronously cancel. For now, we add an RAII stats
counter to track the number of pending cancellation coroutines that are self-owned,
but we should eventually add a global babysitter.

### Field traversal & ordering

Field streaming order is strictly deterministic and governed by the request's canonical schema rather than the client's raw JSON key order or filter registration order:

1. **Canonical DFS Traversal:** The Filter Manager performs a Depth-First Search (DFS) over the request index tree based on the schema's canonical field sequence:
   - Array elements (such as `messages[0]`, `messages[1]`, `tools[0]`) are always traversed sequentially in ascending index order.
   - Object properties follow the canonical schema hierarchy (e.g., `messages` → `tools`).

2. **Independence from Registration Order:** If a filter registers `tools[].function.description` before `messages[].content` in its `FieldStreamingSpec`, `FieldStreamingSession::next()` will still deliver `messages[].content` first if it precedes `tools` in the schema. Filters use `r->field_path()` on `FieldStreamReceiver` to inspect the field identifier.

3. **Single-Pass Coalesced I/O:** Enforcing canonical DFS ordering ensures that reading offloaded buffers from storage is strictly sequential, allowing all filters in the stage to share a single, coalesced read stream without random disk seeks.

4. **Out-of-Order Handling via Staging:** If a filter must inspect a field out of schema order (e.g., inspecting `tools` before making routing decisions on `messages`), it initiates a dedicated pre-forwarding streaming pass via `AiRequest::stream()` before propagating the request index.

### Reserialization

Ordering of JSON fields should be preserved in the index to ensure we can
reserialize into a normalized wire format.

The first filter can be the IR-conversion filter.

We delegate normalization and transcoding to the filter chain. A normalization
filter can be added to re-order the fields. It can apply provider-specific logic
to transform, modify, and keep or remove unknown fields.

Delegating all the above to the filter chain avoids making the core of APM too
model provider-specific.

### Random notes:

Only start streaming if we reach the end of request propagation or a filter
starts streaming. (Can optimize to start early if the first buffer in queue is
interested, and a filter has forwarded the request. We can optimize to overlap
stages - a field will be processed by source() if the previous stage has
finalized the given field)

We initially don't support offloaded payload modification. When we do, each
stage's sink should open a new external buffer, and write modified buffers to
it. This means JsonWithExternalBuffer should handle multiple external buffer
references. We want to have change detection in `FieldStream`.

The last sink should reserialize the JSON DOM back to the HTTP filter chain,
while building a new JsonWithExternalBuffer object with offloaded fields pointing
to the new offsets of the reserialization. This is useful for later filters that
might want to access the JSON payload without parsing the DOM themselves. It
could be a later instance of APM itself. This makes it possible to split the
APM into multiple places of the HTTP filter chain and make the last one do the
transcoding.

The later APM will have the guarantee that fields come in the correct order. If
its filter chain is single pass, no further external buffer is involved.
